# 6-B 일반 업무 동시 수정과 저장 확인

기준: `4b7231cfe56a7f42f7018a85a876195710c49d35` (`refactor/phase6a-save-command`). 결과 브랜치: `refactor/phase6b-save-conflicts`.

## 실제 적용 범위

6-A가 전환한 **독립적인 미완료 일반 업무의 수정 폼**에만 적용했다. 기존 saveState API, schema11, ID, 완료 이력, 생성키·suppression·첨부 참조는 유지한다. 신규 등록/삭제 UI, 프로젝트, 반복 생성, 백업 전체 복원, Drive 업로드는 기존 경로다. main/운영 배포/운영 Firebase·Drive/규칙을 변경하지 않았다. 새 도구나 서버를 설치하지 않았고 Emulator 다운로드를 재시도하지 않았다.

| 책임 | 6-A | 6-B |
|---|---|---|
| 일반 수정 전송 | 전체 snapshot queue/여러 청크 | 명령의 대상 업무·체크만 하나의 트랜잭션 |
| 기준 비교 | 로컬 expected 일치 | 편집 기준·최신 서버·요청 결과의 3방향 비교 |
| 다른 기기 변경 | 수정 필드 patch로 덮어쓸 위험 | 같은 필드 충돌, 독립 필드만 병합 |
| 불명확한 전송 | 일반 offline batch fallback 가능 | 해당 명령은 fallback 금지, 확인 필요 상태 |
| 화면 | 오류 toast/입력 유지 | 상태·기준값·입력값·서버값·충돌 필드 패널 |
| 재연결 | 후속 확인 없음 | 사용자가 읽기 전용 확인 또는 미전송 입력 저장을 선택 |

`js/task-save-conflict.js`는 DOM/SDK 없는 비교·조건부 메모리 반영 모듈이다. `save-command-adapter.js`는 ChangeSet/context를 기존 saveState(meta)에 전달한다. cloud `save`는 taskCommand가 있는 수정만 `saveTaskCommand`로 보내며 나머지는 기존 큐를 사용한다. `commitTransaction`/생성키 잠금 및 백업 remote-conflict 검사는 교체하지 않았다.

## 서버 필드 충돌 계약

1. 실제 개인 Firebase projectId + UID를 명령 context와 비교한다. 기존 다른 저장/백업/복구가 진행 중이면 동시 전송을 보류한다. Firestore 인스턴스도 캡처하여 계정 변경 후 새 업무공간으로 전송하지 않는다.
2. 제출 ChangeSet의 before/after를 schema11 codec으로 정규화한다. 업무 한 개만 직렬화하므로 템플릿·다른 업무의 하위 문서는 포함하지 않는다. 외부 업로드도 실행하지 않는다.
3. 서버에서 업무 revision과 체크 문서 ID 목록을 읽는다. 트랜잭션 내부에서 해당 업무, 연계 문서, 기존/신규/서버 체크 문서를 모두 다시 읽는다. **모든 읽기가 쓰기보다 먼저**다.
4. 명령이 변경하는 필드는 `server == base`이면 적용, `server == desired`이면 이미 반영된 값, 둘 다 아니면 충돌이다. 변경하지 않은 독립 필드와 미해석 업무 필드는 서버값을 유지한다. 서버에서 삭제·완료·연계/반복 전환되었거나 완료 기록이 달라졌으면 일반 수정으로 덮어쓰지 않는다.
5. 체크리스트는 **전체 배열을 하나의 의미 단위**로 비교한다. 서로 다른 체크 항목을 바꿨더라도 두 배열이 달라졌으면 자동 병합하지 않는다. 날짜/start/end/deadline/endRule/unconfirmed/periodLabel도 서로 연관된 필드로 검사한다.
6. 목록 조회와 트랜잭션의 업무 revision이 다르면 쓰기 없이 목록을 다시 조회한다. 최대 3회 후 conflict로 보류한다. SDK 자체 transaction 재실행에도 비교를 다시 수행한다. 별도 무한 재시도는 없다.
7. 업무와 체크 변경 및 로그를 한 트랜잭션에 저장한다. 체크만 수정해도 기존 업무 revision을 증가시킨다. 검사할 체크 ID 합집합이 300개를 넘으면 쓰기 전 거부한다. 해당 명령을 여러 청크로 나누지 않는다. 이미 요청 결과와 같으면 업무·로그 쓰기를 하지 않는다.
8. 완료 receipt는 해당 트랜잭션 응답 또는 **읽기 전용 트랜잭션에서 요청 필드의 최종값을 확인한 결과**다. 단순 온라인 전환, 로컬 캐시 성공, 실시간 snapshot 수신은 명령의 saved 근거가 아니다.

`revision`은 기존 문서 metadata를 사용하며 schema11 일괄 변환이나 영속 operation 문서는 추가하지 않았다. 같은 최종값의 확인은 그 값이 현재 서버에 있다는 의미이며 특정 operation이 역사상 정확히 한 번 실행되었다는 증명은 아니다.

### 체크 문서와 구형 클라이언트의 제한

Web SDK transaction은 이 경로에서 query 전체를 원자적으로 읽지 못하므로 목록을 사전 조회하고 업무 revision으로 경계를 검사한다. **이 경로로 체크를 변경하는 클라이언트끼리**는 업무 revision을 함께 바꾼다. 기존 체크 토글/구형 클라이언트가 부모 revision을 바꾸지 않고 새 체크 문서를 추가하면 목록 phantom을 완전히 검출할 수 없다. 이미 알고 있는 체크 문서 변경은 transaction.get의 재시도 검사를 받는다. 구형 저장 경로의 무조건 덮어쓰기까지 차단하는 Security Rules/CAS를 배포한 것은 아니다. 이를 전체 앱의 동시 편집 안전성이 완성되었다고 해석하면 안 된다.

## 상태·입력·복구 정책

- `saving`: 트랜잭션 또는 명시적 서버 확인 진행 중.
- `pending-sync`: 오프라인 입력이 로컬에 보관되었거나 서버 미반영을 확인한 상태. 인터넷 연결만으로 saved가 되지 않는다.
- `saved`: 해당 명령의 최종값이 서버에서 확인되었고 현재 호출의 로컬 캐시 저장도 종료되었다. 이후 추가 입력까지 저장되었다는 의미는 아니다.
- `conflict`: 같은 필드/보호 기록/편집 기준 충돌. 폼과 메모리 입력을 유지한다. 패널은 기준·사용자 제출·마지막 서버값 및 이유를 textContent로 표시한다.
- `failed`: 저장 전 검증/크기 제한/확정적인 권한 거부 등 명백한 실패. 입력은 유지한다.
- `recovery-required`: 응답 유실, transaction 결과 불명확, 캐시 실패, 저장 중 계정 변경 등. 자동 재전송하지 않는다.

패널의 **서버 반영 다시 확인**은 Firestore 쓰기 없이 값을 검사한다. 미전송 오프라인 입력은 **서버 검사 후 보관한 입력 저장**을 명시적으로 승인한 경우 같은 operationId/기준으로 재검사·저장한다. 충돌이면 저장하지 않는다. 응답 불명확 상태에서 값이 아직 확인되지 않으면 recovery-required를 유지하며 재전송 버튼을 제공하지 않는다. 캐시는 확인 시 현재 입력을 다시 보관할 수 있으므로 “읽기 전용”은 서버 쓰기에 대한 설명이다.

서버값으로 강제 교체하거나 “내 값으로 덮어쓰기”를 제공하지 않는다. 해결되지 않은 충돌은 사용자가 입력을 별도로 보관하고 서버와 비교해야 한다. 확인 후 서버값이 일치하면 다음 수정 세션을 준비한다. 새 세션에서는 직전 제출 폼과 달라진 필드만 보내, 병합된 다른 기기의 값을 오래된 폼으로 다시 덮어쓰지 않는다.

저장 중 추가 편집은 제출값과 현재값이 같은 필드에만 서버 결과를 반영하여 보존한다. 전체 state rollback은 하지 않는다. 미확정 명령이 있는 동안 realtime 전체 교체·기존 snapshot 저장·백업 시작을 보류한다. 그렇지 않으면 전체 저장 래퍼가 미확정 입력을 검사 없이 전송할 수 있기 때문이다. UI의 다른 작업은 메모리에 남을 수 있으며 서버 저장은 확인이 끝날 때까지 보류된다.

서버 반영 후 교정된 현재 state를 기존 직렬화된 IndexedDB 저장 큐에 기록하고 나서 command guard를 해제한다. 캐시 실패를 성공으로 표시하지 않는다. 서버 응답 뒤에 도착한 realtime record 변경을 과거 transaction 결과로 무조건 덮어쓰지 않는다. 그럼에도 IndexedDB와 Firestore는 서로 다른 저장소여서 완전한 원자성을 제공하지 않는다.

## 검증

```sh
node tests/run.cjs --conflicts-only
node tests/run.cjs --commands-only
node tests/run.cjs --backups-only
node tests/run.cjs --atomicity-only
npm test
```

신규 `CONFLICT-01~25`, `CONFLICT-UI-01~04`는 실제 생산 함수 + 모의 Firestore transport 또는 격리 Chromium + 모의 저장 포트를 사용한다. 동시 두 클라이언트, 필드 충돌/병합/같은 결과, revision 재조회·재실행, 체크 배열/추가/삭제, 완료 보호, 오프라인/계정 전환, 응답 유실과 읽기 전용 확인, 추가 편집 보존, legacy snapshot 차단, 큰 묶음 거부, 기존 청크 부분 성공의 오류 증거, 미해석 체크 metadata, 템플릿 격리, realtime/백업 경계, 실제 폼 충돌 표시·후속 수정을 확인한다.

실제 Firebase SDK/Emulator 동시성 실측은 **수행하지 않았다**. 기존 Emulator 13개 NOT_RUN은 5-B②의 실행 파일 다운로드 실패를 그대로 유지한다. 테스트 harness의 새 전역/함수 주입만 보완했으며 기존 250개 ID·제목·기대값을 유지했다. **최종 279개: PASS 262 / XFAIL 4 / FAIL 0 / XPASS 0 / NOT_RUN 13. 신규 29개 PASS, 기존 250개 분류·제목·기대/관측값 보존.** 전체 결과와 비교 증거는 `after-results.json`, `baseline-comparison.json`을 참조한다. 전체 회귀는 마지막에 한 번 실행하며 NOT_RUN 때문에 명령 종료코드는 1이다.

## 남은 위험과 6-C 실측 우선순위

1. 실제 demo Emulator에서 13개 기존 검사 및 신규 일반 업무 동시 수정/재실행/규칙 거부/응답 지연을 실제 SDK로 실행한다. 실제 운영 API에 접속하여 검증하지 않았다.
2. 구형 저장 경로/체크 토글의 부모 revision 참여, 목록 phantom 및 Security Rules의 revision 조건을 함께 설계·검증한다. 규칙 배포 전 전체 허용으로 완화하지 않는다.
3. 일반 등록/삭제, 프로젝트, 백업, 반복, Drive는 아직 서로 다른 경계다. legacy 여러 청크 저장은 부분 성공할 수 있으며 본 명령은 그 실패를 복구하지 않는다. 한 명령도 Firestore 자체 요청 크기/규칙 접근 예산 제한으로 거부될 수 있다.
4. 영속 operation journal이 없다. 대기 기준·guard·operation 결과는 페이지 세션에만 있다. **미확정 상태에서 새로고침하면 안전한 대기 명령 재개를 보장하지 못한다.** 입력은 IndexedDB에 남을 수 있으나 이전 기준/전송 여부를 복원하지 못한다. 새로고침/종료 전 입력을 별도로 보관하고 서버 상태를 확인해야 한다.
5. 충돌 해결 화면, 사용자가 선택한 서버값 재불러오기, 캐시/서버 불일치 복구, pending 상태의 자동 읽기 확인, 큰 체크 목록을 위한 별도 저장 계약은 후속 작업이다. 현재는 명시적 확인을 요구하며 강제 덮어쓰기를 하지 않는다.
6. 사용자 입력/보호 기록을 포함한 오류 객체는 콘솔로 출력하지 않는다. 새 상태·충돌 payload는 세션 메모리와 폼에서만 다루고 로그 문서에는 기존 변경 필드 요약만 기록한다. 운영 인증/Drive 연결을 검증하거나 변경하지 않았다.

## 롤백

전용 브랜치에서 `git revert <6-B 결과 커밋>`으로 코드·script 로딩·테스트를 함께 되돌린다. main reset/force push/스키마 역변환/데이터 삭제는 필요 없다. 이미 반영된 업무나 revision을 되돌리는 작업은 아니다. 미확정 입력과 서버 상태를 보관·대조한 뒤 롤백하고, 6-A의 일반 업무 동시 수정 덮어쓰기 위험이 다시 존재함을 고려해야 한다.
