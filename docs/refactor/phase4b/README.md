## BUG-03 수정 전후

완료한 A의 저장 일정은 2026-01-01이고, 미완료 B의 시작·종료 상대일수는 +2다. 수정 초안이 A를 2026-01-10으로 바꾸면 이전 코드는 normalize에서 B를 1월 12일로 계산한 뒤 reconcile에서 A만 1월 1일로 복원했다.

| 조건 | 수정 전 | 수정 후 / 동일 기대값 |
|---|---|---|
| `reconcile(state, normalizeProject(draft))` | A=1월 1일, B=1월 12일 | **A=1월 1일, B=1월 3일** |
| A의 임시 날짜가 잘못된 경우 | 완료 원본 복원 전에 날짜 오류 가능 | state를 전달한 normalize는 완료 원본부터 복원하고 검사 |
| 연쇄 A→B→C→D | 잘못된 A 초안이 미완료 후속 단계에 전파 가능 | 완료 원본 고정 후 각 미완료 단계 순차 계산 |

[before-results.json](before-results.json)은 수정 전 실제 함수로 재현한 BUG-03이다. 기존 기대값 `['2026-01-01', '2026-01-03']`과 호출 형태를 그대로 두고 정상 PASS assertion으로 전환했다.

## 완료 단계의 기준일 선택

1. 계산에 전달된 현재 `state.projects`와 `state.tasks`를 프로젝트 ID·단계 ID로 연결한다. 원본을 변경하지 않는다.
2. 연결 업무가 `status === 'done'`이거나 `actualComplete`를 가지면 완료 단계로 고정한다. 저장된 프로젝트 단계 전체를 초안에 먼저 복사한다. 체크리스트·참여자·자료·날짜 규칙·단계 ID를 임시 입력으로 변경하지 않는다.
3. 완료 단계 뒤의 기준일은 **연결 업무에 저장된 `task.end`**, 즉 해당 단계의 계산·저장된 예정 종료일이다. 이는 `endType: after`나 휴일 이동까지 적용되어 저장된 날짜이며, 나중에 바뀐 휴일 달력으로 완료 단계의 옛 규칙을 다시 실행하지 않는다. `actualComplete`는 대체 기준일로 사용하지 않는다.
4. 완료 업무 객체는 기존 `buildStageTask`의 원본 반환 경로를 그대로 사용한다. 시작·종료·상태·완료일·completionHistory·첨부 참조·ID가 유지된다. 저장된 단계 객체도 normalize의 일반 정규화 대상에서 제외한다.
5. 완료 단계 원본이 없거나 stage.taskId가 실제 업무와 다르거나 예정 종료일이 없으면 저장을 중단한다. 중복 업무 연결도 거부한다. 불완전한 역사 자료를 현재 초안이나 실제 완료일로 추정해 복구하지 않는다.

중간 완료 단계도 같은 규칙을 적용한다. 앞쪽 진행 단계가 이동해도 완료 단계 자체는 움직이지 않고, 그다음 단계는 해당 완료 단계의 저장 종료일부터 다시 계산한다. 명시적으로 재개한 업무는 진행 단계로 계산할 수 있으며 이전 completionHistory는 유지한다. 이력이 있는 단계 삭제를 차단하는 3-C 정책은 그대로다.

## 실행 순서와 호환 API

`calculateSchedule`은 초안을 복제하고 `scheduleRecords`로 완료 원본을 찾은 다음, 완료 단계를 복원하고 누락 offset을 초기화한다. 그 뒤 미완료 단계만 앞에서 뒤로 계산한다. 전체 계산이 성공하면 `commitSchedule`이 날짜 필드를 반영한다. 계산 중간에 오류가 나면 전달된 초안과 저장 상태 모두 부분 결과를 받지 않는다. 진행 단계의 체크리스트·자료 객체 참조를 유지하므로 기존 UI 이벤트 연결도 유지된다.

| 함수 | 변경 계약 |
|---|---|
| `initializeRelativeDates(project, holidayCheck, state?)` | 완료 원본을 먼저 적용하고 누락 offset을 초기화. 이미 저장된 구형 단계의 offset은 편집 전 원본 단계 쌍에서 도출. |
| `applyRelativeDates(project, holidayCheck, state?)` | 완료 단계를 건너뛰고 미완료 단계만 순차 재계산. 성공 시에만 초안에 반영. |
| `normalizeProject(draft, holidayCheck, state?)` | 계산에 state 전달, 완료 원본은 일반 정규화로 변경하지 않음. 원본 초안은 불변. |
| `reconcile(state, project, holidayCheck)` | state를 사용해 normalize/계산을 다시 수행한 후 결과를 구성. 이전 호출자가 미리 normalize한 경우도 저장 경계에서 보호. |
| `stageEnd(step, holidayCheck, task?)` | 완료 task가 주어지면 저장 예정 종료일 반환. 그 외에는 기존 DateOnly 연결 규칙 유지. |

기존 인자 형태는 호환된다. 다만 state 없는 계산만으로는 완료 여부나 원본 기록을 알 수 없다. 기존 프로젝트를 편집하는 UI는 반드시 state를 전달한다. 최종 reconcile은 언제나 state를 사용한다. 상태가 없는 외부 호출자가 이미 잘못된 완료 초안을 normalize하다 실패하는 것까지 후속 reconcile이 취소할 수는 없으므로 해당 호출자도 선택적 state 인자를 전달해야 한다.

새 업무·단계 추가 시 필요한 ID 생성은 기존 함수를 사용한다. 기존 업무·단계·프로젝트 ID를 재발급하지 않는다. 새 필드, 저장 스키마, 컬렉션, 자동 마이그레이션은 없다. 순수 재계산을 반복해도 일정·offset·이력은 추가 변경되지 않는다. 기존 normalize의 저장용 `updatedAt` 시각 갱신은 유지한다.

## 상대일수와 휴일 규칙

- 2단계 이후 `relativeStartDays`와 `relativeEndDays`는 모두 이전 단계의 유효한 예정 종료일에 더하는 **달력일 offset**이다. 음수·양수는 같은 WMDateOnly 산술을 쓴다. 기존 저장된 상대일수를 영업일 수로 재해석하지 않는다.
- 첫 미완료 단계는 자신의 시작일과 `same/date/after` 규칙을 유지한다. `after` 기간의 `includeHolidays`와 종료일 `holidayShift`는 기존 의미대로 적용한다. 후속 단계에서도 기존 휴일 이동 설정을 유지하며 이동 후 종료일이 다음 단계의 기준이 된다.
- 누락된 구형 offset은 원래 저장된 앞뒤 단계로부터 도출해 초안 날짜 변경 때문에 간격까지 다시 추정되는 일을 막는다. 새 단계는 편집 중 앞 단계와 입력한 날짜로 초기화한다.
- 단계를 재정렬하면 미완료 단계는 새 순서의 앞 단계를 따르고, 완료 단계는 위치가 바뀌어도 고정된다. 첫 위치의 미완료 단계는 자신의 절대 일정을 사용한다. 새로운 완료 이력이나 ID를 만들지 않는다.
- 라이브러리 최초 등록은 기존 `createProjectFromLibraryV175`의 영업일/기간 계산을 그대로 사용한다. 계산된 날짜 차이가 프로젝트의 달력일 offset으로 저장되는 기존 동작도 유지한다. 예를 들어 금요일 10월 23일 다음 영업일이 연휴 뒤 10월 28일이면 저장 offset은 +5다. 이후 프로젝트 기준일을 10월 30일로 바꾸면 +5인 11월 4일로 이동한다. 라이브러리 원래 규칙을 다시 실행하는 방식으로 이번에 바꾸지 않았다.

4-A의 날짜 범위 및 탐색 한도 오류를 그대로 사용한다. 종료일이 시작일보다 이르거나 상대일수가 유효하지 않으면 계산을 중단한다.

## 편집 화면과 저장 일치

`openEditor`, 날짜 입력(시작·종료), 상대일수 입력, 기간 방식/휴일 설정, 단계 추가·삭제·화살표 이동·드래그 이동·탭 전환에서 공통 `recalculateEditor`를 사용한다. 계산 결과 문구를 갱신하고 오류는 화면에 표시하며 저장 버튼을 비활성화한다. 완료 단계 화면은 기존 읽기 전용 정책을 유지하며, 담당자/체크리스트 자동 정규화로 완료 초안을 덮어쓰지 않는다.

`saveEditor`는 자료 업로드 전과 업로드 후에 현재 state를 전달해 검사한다. 날짜 계산 실패는 업무 저장을 시작하지 않는다. 이후 저장 서비스 실패는 기존 메모리 복구 경로를 유지한다. 오류 메시지는 입력 중인 값과 함께 남아 수정할 수 있다. 취소는 초안을 폐기하고 저장을 호출하지 않는다.

Chromium에서 검증한 화면 증거는 SCHED-UI 결과에 포함된다. 완료 1단계 다음 상대일수를 -1/+3으로 입력하면 `2025-12-31 ~ 2026-01-04`가 즉시 표시되고 같은 일정이 저장·재열기된다. 첫 단계 시작/종료 수정 후 후속 일정, 신규 단계의 순서 이동 후 표시와 저장값 일치, 잘못된 구간의 저장 비활성화, 취소 시 저장 호출 0도 확인했다. 실제 라이브러리 등록 함수를 브라우저에서 실행해 최초 영업일 계산과 이후 offset 의미를 함께 검사했다.

## 남은 위험과 5단계 대상

남은 XFAIL은 BUG-01(Tasks 모델 파일), BUG-02(CSS), BUG-08(템플릿 체크리스트), BUG-09(일반 저장의 첨부 임시 데이터), BUG-10(cycleMonths), BUG-11(half), BUG-12(생성키)다.

완료 원본 연결이나 저장 종료일이 불완전한 과거 데이터는 편집 저장이 차단될 수 있다. 자동 수정/추정은 하지 않는다. 옛 BUG-03으로 저장된 미완료 일정은 다음 편집 시 현재 원본과 offset에 맞게 다시 표시될 수 있지만 백그라운드 일괄 수정은 없다. 원격 동시 편집과 저장 트랜잭션의 원자성은 기존 저장 엔진의 한계가 남는다. 자료 업로드 이후 저장 실패 시 이미 올라간 파일을 이번 계산 코드가 분산 롤백하는 것은 아니다.

다음 5단계에서 다룰 후보는 다음과 같다. 이번에는 구현을 변경하지 않았다.

| 경로 | 함수/대상 | 검토 내용 |
|---|---|---|
| `index.html` | `calcByModeV6`, `shiftWorkday`, 일반 `addDays`/`addBusinessDays` | DateOnly 연결, 탐색 제한과 오류 계약 |
| `index.html` | `initialStageScheduleV10`, `createProjectFromLibraryV175` | 라이브러리 최초 영업일/기간 규칙과 프로젝트에 저장한 offset의 의미 명시 |
| `index.html` | `dbLinkedScheduleBasisV151`, `linkedStageDatesV152`, 여러 `recalcLinks` | 부모 실제/예정 기준과 자식 기준 기한의 차이, 완료 고정, 반복 재정의 정리 |
| `js/project-ui.js` | `installRollingRecurrencesV181` 내부 `scheduleKind`, `addMonths`, `dueShift`, `ensureOccurrences` | 월·반기 규칙, 완료 회차 보존, 지속 생성키, BUG-10~12 |
| `js/project-ui.js` | 라이브러리 `shiftDate` 및 휴일 콜백 | 지역 Date 사용을 명시적 달력 입력으로 전환할 범위 |

일반 업무와 반복 엔진의 모든 날짜 문제가 해결된 것은 아니다. 기존 로컬 Date 휴일 콜백과 시계 기반 완료 timestamp 경로는 이번 범위 밖이다.
