# 운영 전환 전제와 롤백

이번에는 배포하지 않는다. 실제 운영 규칙·자료는 미확인이다. 테스트 규칙을 그대로 복사하면 안 된다.

1. 별도 승인 후 실제 개인 Firebase 프로젝트, 승인 UID/공동 UID, 기존 rules의 겹치는 wildcard를 확인해야 한다. tests의 synthetic-owner/demo-work-manager를 실제 값으로 대체하고 해당 프로젝트별 검증을 해야 한다. 단순 로그인된 모든 UID 허용으로 바꾸지 않는다.
2. **기존 자료 검토가 필수다.** legacy task에 키가 있는데 canonical lock이 없거나 소유자가 다르면 이미 만들어진 중복을 Rules만으로 검색·정리할 수 없다. 사전 읽기 검토와 사용자 승인 없는 lock 재발급/자동 병합은 하지 않는다. 키 없는 회차, orphan 체크, 비정상 revision, 비표준 lock ID도 수동 검토 대상으로 분리한다. 실제 앱의 shadowMaps에 잠금이 없으면 자동 보충이 unpaired-lock/invalid-lock으로 보류될 수 있다. Rules가 기존 동일 키 update를 허용한다는 검사는 모든 불일치 자료의 앱 저장이 가능하다는 뜻이 아니다. 이 조건이 남으면 안전한 완전 전환을 완료했다고 할 수 없다.
3. 호환 클라이언트를 먼저 별도 승인·배포하고, 모든 브라우저의 서비스워커·정적 module 캐시 갱신 및 재로그인을 확인한다. 오프라인 대기 쓰기와 journal은 내보내기/확인 후 정리한다. 이 준비 동안 기존 규칙의 허점은 아직 남는다. 적용 전에 임시 편집 중지 등 별도 합의가 필요하다.
4. 그 다음에만 강화 규칙을 별도 승인·배포한다. 새 클라이언트의 부모 revision/atomic pair 저장을 실제 비운영 프로젝트에서 먼저 통합 검증해야 한다. 구형 클라이언트는 서버에서 permission-denied로 차단한다. Rules는 클라이언트 버전 header를 신뢰하지 않는다. 새 규칙을 배포하고 구형 앱도 무조건 정상 저장된다고 약속하지 않는다.
5. 운영 설정 UI의 `workspace-profile.js:firestoreRulesForWorkspaceUid`는 기존 recursive allow를 출력한다. 이번에는 운영 provisioning 구조를 바꾸지 않았다. **이 생성기를 계속 쓰면 강화 규칙이 덮어써질 수 있으므로, 배포 전 hardened 규칙 생성/표시 경로로 전환하고 캐시된 안내문까지 갱신해야 한다.** 테스트 규칙 강화가 운영 provisioning 자동 전환을 뜻하지 않는다.
6. 백업은 기존 완료 이력 보존 정책을 적용한다. 삭제 잠금이 남은 업무 복원, 부모 없는 체크, 이미 존재하는 noncanonical/불일치 키의 복원은 자동 예외 허용하지 않는다. 원본 복구본과 입력을 보존한 후 수동 검토한다. 대형 템플릿/단일 업무가 320 writes 또는 문서 접근 20을 넘으면 명시적 저장 거부로 안내해야 한다.

롤백: 개발 브랜치에서는 6-E 커밋을 revert하여 6-D 테스트·클라이언트 상태로 돌아갈 수 있다. 운영은 미배포이므로 현재 운영 데이터 rollback은 없다. 향후 규칙을 먼저 강화한 상태에서 구형 클라이언트만 되돌리면 체크 저장이 거부될 수 있으므로 규칙/클라이언트를 함께 검토해야 한다. 보안 규칙을 recursive allow로 자동 되돌리는 절차는 제공하지 않는다. 미확정 journal·완료 이력·생성키는 삭제하지 않는다.

남은 한계: 인증/규칙 전체 운영 실측, 신뢰할 수 없는 legacy 잠금 현황, 모든 저장 경로의 의미적 충돌 보호, 청크 간/IndexedDB 간 전역 원자성은 미해결이다. revision fence는 저장 순서 검증이며 구형 일반 저장의 모든 필드에 3-way merge를 새로 제공하지 않는다. 승인 UID가 생성키/반복 표시를 아예 숨겨 일반 업무처럼 만든 데이터의 의미적 중복을 규칙이 추론할 수는 없다.
