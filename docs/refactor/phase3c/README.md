# 3-C 완료 업무 이력 보호

기준: `refactor/phase3b-credential-security` / `7da8ed981605931c1f31a2d72f3e5e07542ef474`
결과: `refactor/phase3c-completion-history`

기존 분석 02·05·07 및 2단계 결과를 재사용해 TD-02의 완료 상태·단계 삭제·명시적 재개 경로만 수정했다. main 병합, 배포, 실제 Firestore 읽기/쓰기, Drive 파일 작업, 인증 구조 변경은 수행하지 않았다. 새 패키지나 프레임워크를 설치하지 않았다.

## 완료 이력 보존 정책

| 상황 | 처리 |
|---|---|
| `status === 'done'` 또는 완료일 존재 | 완료 기록으로 취급한다. 일반 수정으로 업무명·담당·일정·완료일·수행 기록·체크리스트·첨부 참조를 바꾸지 않는다. |
| 완료 단계에 체크리스트 추가/수정 | 편집 화면을 읽기 전용으로 표시한다. 모델에 수정된 초안이 직접 들어와도 기존 완료 업무와 단계 원본을 유지한다. 자동 재개하지 않는다. |
| 프로젝트 전체 수정/단계 순서 변경 | 진행 단계는 기존 방식대로 저장하며 완료 업무 객체와 단계 기록은 보존한다. 완료 업무명·단계 순번은 당시 기록을 유지하므로 현재 프로젝트명·순서와 다를 수 있다. |
| 완료 이력 있는 단계/프로젝트 삭제 | 삭제 전에 차단하고 안내한다. 별도 아카이브로 옮기거나 연결을 끊지 않는다. 재개한 단계도 과거 이력이 있으면 삭제할 수 없다. |
| 명시적 재개 | 사용자 확인 후 현재 완료 업무 전체의 스냅샷과 재개 시각을 남긴 다음 진행 상태로 바꾼다. ID·체크 항목·첨부 참조는 유지한다. |
| 진행/예정 업무의 체크리스트 전체 완료 | 기존 자동 완료를 유지한다. 재개 직후 모든 체크가 남아 있더라도 프로젝트 저장만으로 다시 완료하지 않는다. 체크 변경 또는 명시적 완료가 필요하다. |
| 반복 수정/재개 버튼 재실행 | 일반 수정은 이력을 생성하지 않는다. 이미 진행 상태인 업무의 재개는 무동작이다. 다시 완료 후 재개하면 별도의 회차를 기록한다. |
| 새 업무 복제/반복 발생 | 새 업무에는 원본의 과거 완료 이력을 복사하지 않는다. 기존 회차를 통째로 교체하는 구형 반복 재생성은 완료 이력이 있으면 차단한다. 구형 자동 복구도 완료 기록을 교체하지 않는다. 날짜 생성 규칙은 그대로다. |

일반 완료 업무는 읽기 전용 상세, 업무 복제, 첨부 열기, 명시적 재개를 제공한다. 프로젝트 상세와 재개된 업무 상세에서 이전 완료 기록을 펼쳐 조회할 수 있다. 과거 기록의 첨부는 기존 Drive/local ID로 열며 파일 복사·삭제·변경을 하지 않는다. 편집 화면을 연 뒤 업무가 완료된 경우에도 저장 시 현재 상태를 확인한다.

## schema11 호환 방식

기존 `tasks` 객체에 사용자의 **명시적 재개 시에만** 선택적 `completionHistory` 배열을 추가한다. 자동 데이터 변환, schemaVersion 변경, 새 컬렉션, 업무 ID 재발급은 없다. 기존 업무 데이터는 해당 명령 전까지 새 필드를 갖지 않는다.

```json
{
  "completionHistory": [{
    "id": "fixture-task:completion:1",
    "reopenedAt": "2026-10-23T03:00:00.000Z",
    "snapshot": {
      "id": "fixture-task",
      "status": "done",
      "actualComplete": "2026-10-01"
    }
  }]
}
```

위 예시는 축약형이다. 실제 snapshot에는 기존 업무의 모든 필드를 깊은 복사로 보존하고, `completionHistory` 자체만 제외해 재귀 중복을 막는다. 첨부는 원래 메타데이터를 그대로 보존한다. 업무·프로젝트·단계 ID와 알 수 없는 기존 필드도 보존한다. 기존 schema11 직렬화/역직렬화 함수로 이 배열의 왕복을 검증했다. 서버 규칙과 실제 SDK 저장까지 검증했다는 뜻은 아니다.

재개 후 객체의 JSON UTF-8 크기가 512 KiB를 넘으면 원본을 바꾸기 전에 안내하며 차단한다. 과거 기록을 잘라 버리지 않는다. Firestore의 실제 문서·인덱스 제한을 계산하는 완전한 검증기는 아니며, 큰 문서는 별도 보관 설계가 필요하다. 재개 저장 실패 시 메모리의 업무·프로젝트 종료 표시·목록 선택을 복구한다. 이미 일부 서버 쓰기가 성공한 경우의 분산 롤백을 보장하지 않는다.

### 계약 변경과 해결 오류

- **BUG-04 → PASS:** 동일 완료 업무에 미완료 체크 항목을 추가하는 입력과 기존 기대 완료일을 유지했다. 완료 업무 전체가 원본과 동일하다는 검증을 추가했다.
- **BUG-05 → PASS:** 이전 계약은 단계 제거 후에도 해당 업무가 남아 있어야 한다는 것이었다. 이번 사용자 지시의 대안인 **파괴적 삭제 차단**을 선택했다. 같은 완료 단계 제거 초안을 넣고, 저장 전 예외·전체 입력 불변·업무 ID/완료일 보존을 검증한다. 삭제를 성공으로 처리하거나 기대값을 약화하지 않았다.
- **MODEL-05:** 이전 정상 검사는 완료된 체크를 해제해 즉시 진행으로 돌아가는 동작이었다. 새 정책에 따라 먼저 체크 변경 거부와 스냅샷 보존을 확인하고, 명시적 재개 후 체크 해제가 되는지 검사한다.
- **BUG-03:** 예상 `2026-01-03` 대비 실제 종속 단계 날짜 `2026-01-12`라는 기존 실패 서명이 그대로다. 계산 코드는 수정하지 않았고 4단계 공통 엔진 대상으로 남긴다.
- 나머지 XFAIL은 BUG-01·02·06·07·08·09·10·11·12다. 기존 assertion과 실패 서명을 유지한다. 특히 BUG-07 백업 충돌 병합은 3-D 대상으로 남겼다.

## 남은 위험과 사용자 영향

1. 완료 기록의 오탈자/체크/자료도 바로 편집하지 못한다. 먼저 재개해야 하며 과거 기록은 남는다. 완료 이력이 있는 프로젝트의 삭제·단계 제거·구형 반복 일괄 재생성은 별도 아카이브 정책이 마련될 때까지 제한된다.
2. 클라이언트 수준의 보호다. 이전 버전 탭, 직접 DB 쓰기, 동시 수정, 저장소의 전체 상태 덮어쓰기까지 불변성을 강제하지 않는다. 서버 트랜잭션/리비전/규칙은 이번 범위 밖이다.
3. 백업 병합 BUG-07은 여전히 완료 기록을 덮어쓸 수 있다. 3-D에서 충돌 표시와 보존 계약을 다뤄야 한다. JSON 왕복 통과만으로 백업 충돌 안전성을 주장하지 않는다.
4. 첨부 스냅샷은 참조를 보존하며 원본 파일의 버전/존재를 보장하지 않는다. BUG-09의 task 첨부 직렬화 정리 문제도 남는다. 외부에서 삭제된 파일은 열 수 없다.
5. 이력 크기는 재개 횟수에 따라 증가한다. 서버 문서 크기·인덱스 제한과 오래된 클라이언트의 추가 필드 보존은 별도 검증이 필요하다. 이미 소실된 과거 기록을 복구하지 않는다.
6. 일반 업무의 기존 명시적 삭제/휴지통 흐름과 백업 흐름을 전면 재작성하지 않았다. 이번 보호는 일반 완료 편집·체크 변경·프로젝트 단계/프로젝트 파괴적 삭제와 확인한 반복 교체 경로에 한정된다.

배포 검토 전 별도의 합성 데이터용 Firebase 프로젝트에서 완료 → 새로고침 → 명시적 재개 → 저장/재접속 → 이력 조회, 저장 거절, 다른 탭 충돌, 기존 Drive 첨부 열기를 확인해야 한다. 이 작업에서는 실제 운영 계정이나 데이터를 사용하지 않았다.

## 롤백

이번 결과는 전용 브랜치에만 저장하며 운영 배포는 하지 않는다. 코드 검토에서 되돌릴 경우 이 변경 커밋을 `git revert <3-C 변경 커밋>` 하거나 기준 `7da8ed9`에서 별도 복구 브랜치를 만든다. main에 직접 reset/force push하지 않는다.

추후 테스트 환경에서 이 버전으로 이력을 생성했다면 롤백 전에 해당 schema11 문서를 안전하게 보존한다. `completionHistory`를 삭제하거나 일괄 변환하지 않는다. 이전 코드에는 이력 보호가 없으므로 롤백한 상태에서 완료 편집/재개/삭제를 계속하면 새 이력이 보존된다고 보장할 수 없다. 이 문서의 롤백은 코드 복구 절차이며 운영 데이터 자동 변경 절차가 아니다.
