# 3-D 백업 병합·복원 안전성

기준: `refactor/phase3c-completion-history` / `25f0bf06132a697d4784155b6cdc7c96df17e19e`

결과 브랜치: `refactor/phase3d-backup-safety`

기존 분석 02·07·08, 3-C 정책과 87개 결과를 재사용했다. TD-04/BUG-07의 JSON 가져오기·검증·미리보기·저장 경계만 변경했다. main 병합, 운영 배포, 실제 Firebase/Firestore/Drive API 사용, 인증 구조 변경, schema11 마이그레이션은 수행하지 않았다. 기존 설치 도구를 사용하며 새 패키지는 추가하지 않았다.

## 충돌 정책

| 입력 | 처리 |
|---|---|
| 현재에 없는 정상 ID | 추가한다. 프로젝트/업무 참조와 생성키·첨부 충돌 검증을 먼저 통과해야 한다. |
| 동일 ID·동일 내용 | 중복 추가하지 않는다. 객체 키 순서만 다른 경우도 동일하다. 배열 순서는 데이터로 취급한다. |
| 동일 ID·다른 내용 | 차이를 표시하며 기본 선택은 현재 보존이다. 일반 항목만 사용자가 백업 적용을 선택할 수 있다. |
| 완료 상태·완료일·`completionHistory`가 있는 기존 업무 | 현재 객체 전체를 보존한다. 백업 적용을 지정해도 상태·날짜·체크·첨부·과거 이력을 덮어쓰지 않는다. |
| 완료 이력의 추가/수정/삭제/순서 차이 | 충돌로 표시하고 현재 이력 전체를 유지한다. 두 이력을 자동 합치거나 새 회차를 생성하지 않는다. |
| 완료 이력과 연결된 프로젝트 | 프로젝트와 연결 업무를 함께 보존한다. 보호 대상 업무 및 과거 스냅샷이 참조하는 알려진 템플릿 ID도 보존한다. |
| 같은 생성키의 다른 업무 ID | 참조 충돌로 표시하고 새 회차를 추가하지 않는다. 클라우드에서는 삭제된 업무의 기존 generatedKeys 잠금도 검사한다. 입력끼리 중복 생성키가 생기는 결과는 거부한다. |
| 같은 첨부 ID의 다른 파일 참조/이름/MIME/크기 | 참조 충돌로 표시하고 해당 백업 항목으로 현재 참조를 바꾸지 않는다. 남는 참조 불일치는 검증 오류로 적용을 차단한다. |
| 알 수 없는 기존 필드 | 유지하는 객체에 없는 필드를 지우지 않는다. 일반 충돌에서 백업을 선택해도 기존 객체의 누락 필드를 보존한다. 최상위 기존 확장 필드도 유지한다. |

기본 병합은 기존 데이터를 유지하면서 새 항목을 더한다. 보호되지 않은 업무·프로젝트·템플릿·휴일·설정의 수정은 항목별로 명시적으로 백업 적용을 선택해야 한다. 프로젝트 단계와 템플릿 하위 내용도 해당 항목의 차이에 포함한다. 서로 모순되는 선택으로 고아 참조가 생기면 저장할 수 없다.

전체 복원은 백업에 없는 **보호되지 않은** 업무·프로젝트·템플릿·휴일을 제거할 수 있다. 삭제 개수를 미리 보여 주고 별도 동의 체크를 요구한다. 전체 복원도 완료 기록을 파괴하는 예외 권한이 아니다. 완료 이력이 있는 프로젝트의 연결 업무·관련 템플릿은 남는다. 기존 변경이력, 구분·담당자·선택 목록과 알 수 없는 최상위 필드, 로컬 휴일 API 설정은 보존한다. 따라서 백업의 바이트 단위 복제가 아닌 보호 정책을 적용한 복원이다.

## 실제 호출과 저장 순서

이전에는 `importBackup → JSON.parse → tasks/templates 배열 확인` 후 로컬은 상태 대입, 클라우드는 `importState → incoming 우선 mergeById → ensureImageUploads → replaceState → save`였다. 교체 경고를 띄운 뒤 실제로는 클라우드 병합을 하는 불일치가 있었고, 저장 실패 전에 메모리 상태가 이미 바뀌었다.

현재는 두 기존 파일 선택 진입점과 local shim을 같은 검토 절차로 연결한다.

1. `WMBackupUI.openFile → WMBackupSafety.parse/prepare`로 파싱·검증한다. 클라우드는 `previewImport`가 동기화 상태, 계정/원격 기준, 기존 생성키 잠금, 저장 codec의 필드 보존 가능성까지 확인한다.
2. 추가·동일·충돌·삭제 개수, 완료 이력 충돌, 프로젝트/생성키/첨부 참조 충돌, 검증 오류·누락, 현재/백업 필드 차이를 표시한다. 기본은 병합이다. 미리보기와 선택 변경은 상태·저장소를 쓰지 않는다.
3. 명시적 적용 확인 후 순수 모델로 결과를 재계산한다. 미리보기와 다르거나 현재 데이터/연결 계정/수신된 원격 기준이 바뀌면 중단한다.
4. 현재 상태와 검토 결과를 복구용 JSON 객체로 준비해 기존 브라우저 IndexedDB 저장 도우미에 보관한다. 계정·업무공간별 키를 사용한다. 저장소 실패 시 본 데이터 저장을 시작하지 않는다. 대기 중 계정이 바뀌면 다른 계정 키에 원본을 저장하지 않는다. 복구본 준비 후에도 기준을 다시 검사한다.
5. 로컬은 검토 결과를 기존 `writeLocalState`로 저장한다. 클라우드는 기존 `serializeState/diffMaps/commitOnlineChunks/commitTransaction`을 재사용한다. 일반 저장 큐·업무 생성 wrapper와 첨부 업로드는 호출하지 않아 검토 결과에 회차/자료가 추가되지 않는다.
6. 백업 트랜잭션에 한해 생성·수정·삭제·생성키의 원격 현재값을 읽고 기준값과 비교한다. 체크리스트/연계만 바뀌어도 부모 업무를 검사한다. 프로젝트·템플릿 변경도 관련 업무의 동시 완료를 검사한다. 완료한 청크의 기준은 다음 청크에 반영한다. 일반 저장의 기존 정책은 유지한다.
7. 저장 중 도착한 관측 가능한 원격 변경도 재검사한다. 미리보기에 없던 원격 값을 로컬 recordMaps에서 지워 버리지 않는다. 클라우드 저장 후 브라우저 캐시 저장까지 성공한 뒤 `replaceState`로 검토 결과를 반영한다. 정상 경로의 최종 상태는 미리보기 결과와 같다.

클라우드 가져오기는 로그인·온라인·동기화 완료 상태에서만 가능하다. 대기 중인 일반 저장이 있으면 먼저 완료해야 한다. 직접 `importState(data)`만 호출하는 무검토 쓰기도 거부한다. `saveState` 및 cloud 저장 입구는 가져오기 진행/복구 확인 중 추가 저장을 차단한다.

## 입력 검증과 호환성

- 파일/JSON 문자열은 20 MiB 이하로 제한한다. 필수 schema11 배열(tasks/projects/templates/holidays/categories/owners/selectedCategories/changeLogs)과 settings 객체를 요구한다. 스키마 표기가 없으면 경고와 함께 구조로 검증하고, 명시된 다른 버전은 거부한다.
- ID 중복/잘못된 타입, 날짜, 체크리스트, 프로젝트 단계, 완료 스냅샷과 재개 시각, 파일 메타데이터 배열·ID·타입을 검사한다. 잘못된 JSON, 위험한 객체 키, 과도한 중첩, 인라인 파일 본문/임시 URL은 적용할 수 없다.
- 입력 참조와 최종 결과의 프로젝트↔단계↔업무, 상위 업무, 생성키, 첨부 참조를 검사한다. 실제 원격 파일 존재 여부는 API로 조회하지 않는다. 원본 연결이 없는 파일은 경고에 표시한다.
- 기존 schema11 codec이 미해석 필드를 보존하지 못한다면 자동 제거·변환 대신 클라우드 가져오기를 차단하고 손실 경로를 보여 준다. 예를 들어 기존 체크 항목의 임의 추가 속성은 현재 codec이 잃을 수 있으므로 자동 수정하지 않는다.
- 업무·프로젝트·단계·완료 이력·첨부 ID는 재발급하지 않는다. 백업의 변경이력과 알 수 없는 최상위 새 필드는 기존 데이터 위에 자동 이식하지 않는다. 기존 변경이력과 최상위 확장값은 유지한다. 가져오기가 새 완료 회차를 만들지는 않는다.

불완전한 과거 백업, 문자열 사진/인라인 원본을 포함한 구형 백업, 기존 참조가 깨진 작업공간은 이전보다 엄격하게 거부될 수 있다. 오류를 숨기기 위한 자동 보정이나 마이그레이션을 넣지 않았다. 현재 데이터는 보존하고 별도의 호환성 작업으로 다뤄야 한다.

## 복구본과 저장 실패

브라우저의 계정/업무공간별 `backupRecovery:…` 키에 마지막 적용 전 `before`, 검토 결과 `after`, 시각, 방식을 보관한다. 설정의 **가져오기 전 복구본 다운로드**로 before를 JSON으로 내려받는다. 다음 정상 스냅샷 준비 때 같은 계정의 마지막 복구본을 교체한다. 파일 원본은 포함하지 않는다. 복구본은 브라우저에만 있으며 Git이나 Drive에 자동 전송하지 않는다.

취소·검증 실패·미리보기 기준 변경은 본 데이터 쓰기를 시작하지 않는다. 스냅샷 저장 실패도 중단한다. 본 저장에 진입한 뒤 오류가 발생하면 성공 메시지를 표시하지 않고 **복구 확인 필요**를 안내한다. 메모리는 검토 전 상태를 유지하고 추가 저장을 막는다. 클라우드 오류에는 확인된 완료 청크 수/전체 청크 수를 부가한다. 실패한 청크가 서버에 반영됐는지는 통신 오류 시 확정할 수 없다.

**Firestore 여러 청크와 브라우저 캐시는 하나의 원자적 트랜잭션이 아니다.** 앞 청크만 성공하거나 서버 성공 후 캐시 저장이 실패할 수 있다. 백업 저장은 일반 저장의 offline batch fallback으로 재시도하지 않는다. 이전 서버 상태로 자동 덮어써 복구하려 하지도 않는다. 이 경우 복구본을 보존하고 새로고침하여 실제 서버 상태를 읽은 뒤 새 미리보기로 비교해야 한다. 완료 이력을 강제로 지우는 복구 선택은 제공하지 않는다.

| BACKUP-CLOUD-01~08 | 실제 import/transaction 함수의 모의 SDK 검증: 무검토 쓰기 거부, 정확한 결과/이력, 원격·계정 변경, codec 손실 거부, 부분 청크 실패/추가 저장 차단, 생성·수정·삭제/키 잠금 검사, 부모의 새 완료와 늦은 원격 변경 보호 |

순수 검사는 합성 schema11 객체를 사용한다. 브라우저는 기존 로컬 앱을 격리 Chromium에서 실행하고 외부 요청을 차단한다. 저장·첨부 서비스는 mock이다. CLOUD 검사는 실제 저장 함수 코드를 실행하되 Firebase transaction/문서/캐시는 메모리 모의 구현으로 대체한다. 실제 Firebase SDK, 보안규칙, OAuth, 네트워크 단절 후 서버 결과는 검증하지 않았다. 실제 운영 API 검사는 등록하지 않았으며 집계의 NOT_RUN 0이 해당 외부 검증 완료를 뜻하지 않는다.

집중 검사 중 발견한 인라인 파일 탐색 경로 누락을 보완했다. 브라우저 검사에서는 인증을 차단한 shell의 bind 호출과 비동기 파일 읽기 대기를 명시하고, 실제 local shim에 있는 save 경계를 mock에도 구현했다. assertion을 제거하거나 실패를 XFAIL로 바꾸지 않았다.

- `js/backup-ui.js`: 기존 파일 선택의 미리보기·선택·복원 동의·결과/오류·계정별 복구본 다운로드.

## 남은 위험과 사용자 영향

1. 여러 청크 전체의 원자성이나 모든 기기 간 충돌 방지를 보장하지 않는다. 수신/transaction 검사 이후의 추가 원격 수정, 큰 작업의 일부 성공, SDK 응답 불확실성은 남는다. 서버 revision/공간 단위 잠금 설계는 별도 작업이다.
2. 가져오기 실패 시 본 데이터의 메모리 복구와 서버 롤백은 다르다. 서버 쓰기는 자동 취소되지 않는다. SDK/보안규칙과 실제 계정에서 저장 실패·재접속·복구본 비교를 배포 전에 별도 테스트 환경으로 확인해야 한다.
3. 안전한 기본값 때문에 과거 백업으로 완료 상태를 되돌리거나 현재 완료 이력에 백업 이력을 강제로 합칠 수 없다. 보호 프로젝트의 미완료 단계와 연결 템플릿도 가져오기에서 보수적으로 보존한다. 일반 수정/3-C의 명시적 재개는 기존 경로를 사용한다.
4. 20 MiB 파일 제한, 브라우저 quota, Firestore 문서/transaction 제한은 남는다. 복구본이 저장되지 않으면 가져오기를 시작하지 않는다. 브라우저 데이터 삭제·기기 분실 시 로컬 복구본도 없어질 수 있으므로 중요한 복구본은 다운로드해야 한다.
5. JSON은 첨부 원본을 복원하지 않는다. 같은 브라우저/Drive의 기존 ID를 참조한다. 누락·삭제된 실제 파일 존재 여부는 확인하지 않는다.
6. 이 보호는 새 가져오기 경로에 한정된다. 구버전 탭·직접 Firestore 쓰기·다른 일반 편집 경로까지 서버가 강제 보호하는 것은 아니다. 기존 XFAIL 9개는 별도 단계에 남긴다.

## 롤백

전용 브랜치의 3-D 커밋을 `git revert <3-D 변경 커밋>` 하거나 기준 `25f0bf0`에서 별도 복구 브랜치를 만든다. main에 reset/force push하거나 운영 데이터를 자동 변경하지 않는다. 이번에는 운영 적용이 없다.

추후 테스트 환경에서 가져오기를 실행했다면 먼저 계정별 복구본 JSON과 현재 서버 상태를 보존한다. 코드 revert는 이미 저장된 업무를 되돌리지 않는다. 복구본을 새 미리보기로 비교하되 현재 완료 이력은 그대로 보호해야 한다. `completionHistory`나 생성키 잠금·첨부 ID를 지우는 마이그레이션은 하지 않는다. 구버전으로 돌아가면 BUG-07과 무검토 가져오기 위험이 다시 생기므로 그 상태에서 백업 가져오기를 계속하지 않는다.
