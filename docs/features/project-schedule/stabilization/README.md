## 확인·수정

- 기존 단일 업무 명칭, 신규 단계 UI 제거, 단일 라이브러리 분류, 상대/직접 일정 및 라이브러리 추후 직접 선택은 재구현하지 않음. 기존 별도 5개 검사를 전체 실행에 편입.
- 서버 저장 receipt를 반복 보충 wrapper가 버려 프로젝트 생성 성공 후 실패 화면으로 돌아가던 오류: `persistence` 등 반환값 유지. pending-sync를 서버 확정으로 바꾸지 않음.
- 생성 직후 프로젝트 재저장 가짜 충돌: 서버만 동기화 필드를 제거하던 비대칭 비교 수정. `createdAt/updatedAt/revision`은 기존 서버 전용 동기화 메타데이터 규칙을 양쪽에 동일 적용. 단계/이력/날짜 필드는 제외하지 않음.
- Firestore map 키 순서만 다른 경우의 가짜 충돌: 기존 `WMSaveCommand.equal` 사용. 실제 단계 값 수정은 계속 충돌로 거부.
- 프로젝트 저장·폐기 실패 시 전체 tasks/projects 복원으로 동시 입력 소실: 제출 후 그대로인 변경 항목만 복원. 다른 계정 범위에는 복원하지 않음.
- 프로젝트 종료·단계 완료/체크리스트가 일반 저장 경로를 사용하던 문제: 기존 프로젝트 트랜잭션 보호 연결. 단계 수동 완료 화면은 서버 확정까지 유지. 완료 이력 없는 프로젝트만 폐기 가능.
- 라이브러리 프로젝트 등록의 오프라인 거짓 성공: 프로젝트 서버 확인 경계 연결. 다중 프로젝트도 한 저장에서 처리하며 기존 트랜잭션 한도 초과 시 부분 성공으로 쪼개지 않고 거부. 실패 시 다른 입력은 유지.

재현 전 실패 근거는 `*-before.log`에 보존. 이는 합성 데이터이며 운영 기록이 아님.

## 검사 환경

실제 Chromium, loopback HTML 및 실제 제품 `saveState`/반복 wrapper/클라우드 함수. 인증/서버 운송만 합성 대체. UI 검사에서 Firebase SDK 네트워크는 차단. 휴지통 transport도 모의이며 보관 snapshot을 검사. 이를 실제 OAuth/운영 Firestore 검증으로 표현하지 않음.

신규 UI는 프로젝트 생성/지연/수정/추가/재정렬/취소/폐기/완료/실패/응답 유실, 단일 업무 생성·라이브러리·메모 수정·완료·재개·휴지통, 직접 일정 라이브러리 정상/오프라인을 검사. 신규 SDK 2건은 같은 실제 프로젝트 모델(생성/수정 시각 포함)을 독립 클라이언트로 검사하도록 추가.

Cloud 실행 환경에서 Emulator JAR 다운로드 실패. 반복하지 않았으며 환경 로그 보존. 별도 개발 브랜치 Actions는 기존 Node24/Java21/Chromium/Emulator 환경을 사용. `demo-work-manager`와 loopback만 허용; 운영 자격증명/배포 단계 없음.
